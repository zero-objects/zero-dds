Regional / Defense-Vendors

Zusaetzlich zu den Mainstream-Implementationen gibt es eine Reihe regional oder vertikal fokussierter DDS-Vendors. Die Feature-Claims sind hier weniger gut dokumentiert (Closed Source, Defense-Markt), die Eintraege basieren auf offiziellen Produktseiten.

Zu "Israel": Es gibt aktuell keinen bekannten israelischen DDS-Middleware-Anbieter. Was oft verwechselt wird: IAI (Israel Aerospace Industries) setzt fuer ihre OPAL-Avionics- Plattform auf RTI Connext, und es gibt in Jerusalem eine Firma namens "DDS Security", die aber CCTV/Access-Control macht, nicht Middleware. Embedded / Micro-Variante (eigene Kategorie)

Das sind keine klassischen DDS-Implementationen fuer Desktop/Server, sondern extrem kleine Clients fuer Mikrocontroller. Micro XRCE-DDS ist sogar ein eigener OMG-Standard (DDS-XRCE, Client-Broker-Architektur statt peer-to-peer).

Kurz-Profile

  • MilDDS (MilSOFT, Türkei) — seit 2004, COTS-C4ISR-Middleware. CMMI Level 5, "no dynamic memory after init" (wichtig für Safety). Eingesetzt in türkischen CMS/Tactical-Data-Link-Programmen.
  • InterCOM DDS (Kongsberg Gallium, Norwegen) — Voice + Data Intercom, C4ISR. Referenz: US SOCOM Command Craft Medium. Fokus auf low-latency tactical networks.
  • GurumDDS (GurumNetworks, Südkorea) — ROS2-supported RMW (rmw_gurumdds). Proprietär, aber Standard-ROS2-kompatibel.
  • Vortex OpenSplice — Ex-PrismTech (UK), ADLINK akquiriert, jetzt ZettaScale. Federated-Daemon-Architektur (nicht library-per- process wie die anderen). Historisch die stärkste Persistence-Story, schwerer zu deployen.
  • RustDDS (Atostek, Finnland) — Rust-native wie wir + dust-dds, aber kleinerer QoS-Support. Aktiv weiterentwickelt, akademischer Background.
  • Connext Micro (RTI) — Embedded-Variante von Connext, eigene Codebase. Safety-zertifiziert. Kein dynamic discovery (static wiring zur Build-Time).
  • Micro XRCE-DDS (eProsima) — kein echtes Peer-DDS, sondern ein Client-Broker-Standard (DDS-XRCE) für Mikrocontroller. Basis für micro-ROS (ROS2 auf µC). Clients melden sich bei einem DDS-Agent, der im klassischen DDS-Netz als Proxy agiert.
Cyclone-Safety-Zertifizierung (Ergänzung): ZettaScale hat eine kommerzielle Cyclone-DDS-Variante namens Motionwise Cyclone DDS (in Partnerschaft mit TTTech Auto), die ISO 26262 zertifiziert ist — die erste europäische DDS-Implementation, die in Serien-Automobilen zertifiziert eingesetzt ist. DO-178C-Zertifizierung ist für Cyclone bisher nicht bestätigt.
Klärung zu "InterCOM DDS lokal Japan": Das ist eine Verwechslung (aus externer Quelle). InterCOM DDS stammt von Kongsberg Defence & Aerospace, Norwegen — nicht aus Japan. Referenz-Kunde: US SOCOM Command Craft Medium.

Interop-Risiken / Bekannte Quirks

Aus der Recherche herausgefiltert — das sind die Punkte, die unser QoS-Matrix-Harness explizit abdecken sollte:

  1. Cyclone hat keine native Transient/Persistent-Durability. Nur Transient-Local über Writer-History-Cache. Transient kann nur mit externer OpenSplice-Persistence-Service abgerufen werden, nicht intern bereitgestellt. Cross-Vendor-Fallstrick: Ein Fast-DDS- oder RTI-Publisher mit Durability=Transient wird vom Cyclone-Reader nur wie Transient-Local behandelt.
  2. OpenDDS Transient/Persistent funktioniert nicht über RTPS. Die Durability-Service-Features sind an OpenDDS-native Transports gekoppelt — RTPS-Interop-Path ist auf Transient-Local limitiert.
  3. Cyclone/RTI AckNack-Edge-Case: Wenn Cyclone dem RTI-Writer signalisiert, dass alles empfangen wurde, kann der RTI-Writer in einen Endless-Loop gehen. Bekannt aus Community-Forum, Status unklar.
  4. autodispose_unregistered_instances QoS: unterschiedliche Interpretation zwischen Cyclone und RTI.
  5. XTypes-1.3-TypeLookup-Service ist bei den meisten Vendors noch Preview/partial. Type-Evolution-Szenarien (hinzufügen/ entfernen von optional Fields) zwischen Vendors liefern oft keine saubere Matching-Fail-Meldung sondern silent drop.

ZeroDDS — konkrete Ableitungen für die eigene Roadmap

Gewinn-Positionen (heute Parität oder Vorsprung)

  • 33/40 Features voll — über Cyclone (29) und Fast-DDS OSS (29), praktisch gleichauf mit Fast-DDS Pro (34) und RTI Connext (34) — einziges Spec-Defizit ist Safety-Cert (Partnerschaftspfad).
  • no_std-Fähigkeit (einzig wir + Connext-Micro).
  • XTypes-1.3 voller Stack: TypeObjectV2 + TypeLookup + DynamicType / DynamicData + Assignability — RTI hat TypeLookup nur partial, Cyclone hat TypeObjectV2 nur partial.
  • DDS-Security 1.2 voll — Cyclone und Fast-DDS-OSS nur partial; gleiche Klasse wie Fast-DDS Pro / RTI.
  • DDS-RPC voll — Fast-DDS-OSS, Cyclone, OpenDDS haben das nicht; gleiche Klasse wie Fast-DDS Pro / RTI.
  • DDS-TSN voll — Cyclone, Fast-DDS-OSS, OpenDDS haben das nicht; gleiche Klasse wie Fast-DDS Pro / RTI.
  • Rust-native (wir + dust-dds + RustDDS — aber wir haben deutlich mehr QoS als dust-dds).
  • Spec-Coverage strict-auditiert: 31/32 Spec-Coverage-Files voll grün gegen die jeweiligen OMG-/IETF-/OASIS-Specs (siehe docs/spec-coverage/).

Differenzierungs-Features über Mainstream hinaus (Migrations-Hebel)

  • DLRL voll (crates/dlrl/) — kein anderer aktiver Vendor hat das; Sales-Hebel für DDS-1.x-Bestandsmigrationen.
  • DDS-XML 1.0 + DDS-AMQP 1.0 + DDS-OPC-UA + DDS-Web — alle vier als eigene Spec-Coverage-Files voll grün; ZeroDDS positioniert sich als Hub für Cross-Protocol-Bridging.
  • CCM 4.0 + AMI4CCM + CORBA 3.3 + COS-EventService — voll ausgewiesene Stub-Layer als Migrations-Coexistence für Finanz- / Telco-Bestand.
  • DDS-XRCE — Embedded- / IoT-Pfad jenseits der Mainstream-Vendoren.

Verbleibende Defizite

  • Transient + Persistent Service — nur RTI / Fast-DDS-Pro / OpenDDS; Backend ist im DataWriter angeschlossen, Cross-Vendor-Wire-Replay-Pfad fehlt noch.
  • Python-Binding — Riesen-Reichweite-Hebel (ros2-python).
  • Voller C-Binding (FFI-Wrapper auf DCPS-Public-API).
  • Voller C++/Java-Runtime-Wrapper auf DCPS-Public-API (heute nur Codegen + PSM-Skelett).
  • Safety-Cert (DO-178C / ISO 26262) — Partnerschaft, nicht v1.x.
  • Zero-Copy / FlatData — Iceoryx-Integration als opt-in.

Realistische Positionierung v1.2 → v1.3

Heute (v1.2): "Rust-native DDS mit Pro-Feature-Parität (33/40), voller XTypes-Stack, voller DDS-Security 1.2, voller DDS-RPC, voller DDS-TSN, plus DLRL/CCM/CORBA-Coexistence, plus 5 Bridge-Stacks (AMQP/MQTT/CoAP/WebSocket/gRPC), plus no_std."

v1.3-Cluster (zwei Pakete): (a) Python-Binding via PyO3; (b) C-Binding-FFI auf DCPS-API. Damit landen die letzten beiden Sprach-Bindings, die heute fehlen.

Nach v1.3: 35/40 Features = Vendor-Spitze, ohne Safety-Cert.
