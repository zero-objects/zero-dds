## The 4 remaining — proven OpenDDS-side, not "given up"

### 1+2. `data-sign`, `all-sign` — OpenDDS cannot DECODE `data_protection_kind=SIGN` (auth-only payload)

**OpenDDS↔OpenDDS-self: NO_MATCH** (OpenDDS fails talking to itself).
**ZeroDDS↔ZeroDDS-self: green** (39µs / 46µs — ZeroDDS does it fine).

Live error (OpenDDS-self, `OPENDDS_SECURITY_DEBUG=encdec_error`):
```
RtpsUdpReceiveStrategy: decode_serialized_payload failed [-3.3]:
Auth-only payload transformation not supported (DDSSEC12-59)
```
OpenDDS source: `dds/DCPS/security/CryptoBuiltInImpl.cpp` `decode_serialized_payload`
(~L2310): the GMAC/auth-only branch is hard-coded to return `set_security_error(-3, 3, "...DDSSEC12-59")`. The *encode* side can emit a GMAC payload, but the *decode* side refuses it — so even OpenDDS→OpenDDS SIGN payload fails.

Root cause is an **unresolved OMG spec defect, raised by OpenDDS's own maintainers**:
- **OMG issue DDSSEC12-59** "Parsing messages generated by `encode_serialized_payload` (auth only)", reported by Object Computing Inc. (Adam Mitz), 2018-05-09, against DDS-SECURITY 1.1b1. **Status: Closed / Deferred** ("Defer to next RTF") — never fixed. The auth-only payload wraps `SerializedPayload` between a `CryptoHeader` and a *variable-length* `CryptoFooter` with **no in-stream length field**, so the receiver cannot reliably delimit the authenticated bytes. https://issues.omg.org/issues/DDSSEC12-59
- OpenDDS docs list "Signing (without encrypting) at the payload level" as **not implemented**, citing DDSSEC12-59. https://opendds.readthedocs.io/en/latest-release/devguide/dds_security.html

**Verdict: genuine OpenDDS limitation rooted in a deferred OMG spec defect. ZeroDDS can do it; OpenDDS cannot.** Not a ZeroDDS bug, not config.

### 3+4. `all-enc`, `sros2-full` — OpenDDS `check_create_participant` rejects the bench's full access-control config

**OpenDDS↔OpenDDS-self: FAIL — participant create fails** (OpenDDS rejects its own participant).
**ZeroDDS↔ZeroDDS-self: green** (47µs — ZeroDDS creates the participant + full-lockdown roundtrip).

Live error (OpenDDS-self):
```
DomainParticipantImpl::enable, Unable to create participant. SecurityException[-1.0]:
AccessControlBuiltInImpl::check_create_participant: No governance exists for this domain
```
OpenDDS source: `dds/DCPS/security/AccessControlBuiltInImpl.cpp` `check_create_participant`
(~L281-348), a literal implementation of **DDS-Security spec Table 63** (default-deny).
Distinguishing config: these two profiles set `enable_join_access_control=true` +
`enable_read_access_control=true` + `enable_write_access_control=true` (full sros2-style
lockdown); the 9 green profiles have access control OFF (only protection kinds ON).
Governance domain rule is `<domains><id>200</id></domains>` for all profiles (not the issue).

Per **DDS-Security §8.4.2.9.3**, `check_create_participant` consults **both** the governance topology
**and** the participant's **permissions grant**. It returns TRUE if, for a domain rule matching
`domain_id`, the domain is **not** join-access-protected (`enable_join_access_control=FALSE`) **or** the
permissions document holds a grant — valid at the current time — whose `<domains>` matches `domain_id`.
A fully access-controlled governance is therefore **NOT un-joinable**: it is joinable by any participant
whose grant covers the domain.

OpenDDS's `AccessControlBuiltInImpl.cpp` (~L281-348) implements a **stricter, topology-only** reading:
it permits creation only when some topic rule disables read/write AC **or** join-AC is off, and **ignores
the grant clause**. The bench's `all-enc`/`sros2-full` governance has one topic rule
`<topic_expression>*</topic_expression>` with both read+write AC TRUE and join-AC TRUE, so under
OpenDDS's reading neither escape holds → OpenDDS returns FALSE and self-refuses (reproducible
OpenDDS↔OpenDDS). **This is an OpenDDS-specific stance, not a universal spec verdict** — Cyclone DDS and
Fast DDS both join the exact same full-AC governance with a matching grant (see ZeroDDS↔FastDDS `all-enc`
109/123 µs; SROS2's full-lockdown profile relies on precisely this).

**Verdict: full-AC (`all-enc`/`sros2-full`) is joinable per §8.4.2.9.3 with a valid grant.** The
ZeroDDS↔OpenDDS cell is red **only because OpenDDS refuses on its side**; ZeroDDS, Cyclone and Fast DDS
all create the participant. The ZeroDDS↔OpenDDS maximum stays **9/13**, bounded by OpenDDS's stance (and
DDSSEC12-59) — **not** by ZeroDDS.

**Correction of an earlier mis-fix.** A prior pass mis-read this gate as topology-only and bolted a
Table-63 *reject* onto ZeroDDS (`Governance::is_domain_joinable` + `SharedSecurityGate::is_domain_joinable`
+ a create-deny gate) to "match OpenDDS" — even though the evidence index below shows ZeroDDS-self
joining `all-enc` at 47 µs. That reject was **wrong**: it blocked ZeroDDS from every fully-locked secured
domain, contradicting Cyclone/Fast DDS. **Now corrected:** the create gate is grant-based
(`Governance::check_create_participant`, §8.4.2.9.3), wired in `zerodds_runtime_create_secure`; the bogus
`is_domain_joinable` enforcement has been removed. ZeroDDS joins full-AC with a valid grant. Unit test
`check_create_participant_consults_permissions`.
