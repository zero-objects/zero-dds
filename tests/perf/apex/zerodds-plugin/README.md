# Apex.AI performance_test ZeroDDS plugin

CI-3d wave. Bridge plugin so that Apex.AI's `performance_test` can use ZeroDDS
as communicator backend (`--communication ZeroDDS`).

## Architecture

```
Apex performance_test (C++ application)
   ↓
ZeroDdsCommunicator (this plugin)
   ↓
zerodds.h (C FFI, generated by dds-c-api/cbindgen)
   ↓
libzerodds.so (Rust cdylib from crates/dds-c-api)
```

## Standalone build (without Apex/ROS)

```bash
cargo build -p dds-c-api --release  # creates libzerodds.so
cd tests/perf/apex/zerodds-plugin
cmake -B /tmp/build -DZERODDS_HOME=$(git rev-parse --show-toplevel)
cmake --build /tmp/build
# yields /tmp/build/libperformance_test_zerodds_plugin.{so,dylib}
```

Verifies that the plugin links against the C API — without needing
ROS or Apex on the build host.

## In-Apex build (on a host with ROS)

```bash
ssh <user>@<ros-host>
cd ~/performance_test  # Apex repo
ln -s $HOME/zerodds/tests/perf/apex/zerodds-plugin \
      ./performance_test_zerodds_plugin
. /opt/ros/jazzy/setup.bash
ZERODDS_HOME=$HOME/zerodds \
colcon build \
  --packages-select performance_test performance_test_zerodds_plugin
```

## Docker build (CI)

```bash
cd ~/zerodds
ln -s ~/performance_test ./performance_test
docker build -f tests/perf/apex/Dockerfile.zerodds -t apex-perf:zerodds .
```

Multi-stage: the Rust stage builds `libzerodds.so`, the ROS stage builds Apex
with the Cyclone + ZeroDDS plugin packages.

## Bench run

```bash
docker run --rm --net=host apex-perf:zerodds \
  --communication ZeroDDS --topic Array1k --rate 1000 --max_runtime 60 \
  --output_file /tmp/zd_self.csv
```

## Apex plugin API note

Apex.AI's `performance_test` 3.x exposes a
`Publisher`/`Subscriber` interface per vendor in `communication_abstractions/`.
Our plugin delivers the implementation as the ament package
`performance_test_zerodds_plugin` and can be included by Apex's build system
via the plugin selector — the concrete patch in
Apex's CMake (e.g. `-DPERFORMANCE_TEST_PLUGIN=ZERODDS`) requires
an adaptation in their `CMakeLists.txt`. As long as that is not merged upstream,
the run goes through a side-by-side mode:
the ZeroDDS plugin lib is injected at runtime via `LD_PRELOAD`
and forces Apex's default communicator factory to our backend.

## Discovery timing

Endpoint wiring (`wire_writer_to_remote_reader` /
`wire_reader_to_remote_writer`) in DcpsRuntime uses SPDP-discovered
locators. If a writer/reader is created **before** SPDP has seen a
peer, the locator list is empty and the first wire
attempt finds no target.

**Self-healing:** SEDP builtin writers are reliable and keep
their history. As soon as SPDP discovers a peer,
`sedp.on_participant_discovered` sends heartbeats, the peer NACKs, and
the historical pub/sub data is delivered afterwards. `run_matching_pass`
runs on the arrival of every SEDP event and retries the wiring —
this time with a filled SPDP cache. Empirically (5×5 runs on a Linux test host):
end-to-end pub-sub gets through **without** explicit waiting in 600-720 ms.

**Optional helper:** `Communicator::wait_for_peers(min, timeout)`
or `zerodds_runtime_wait_for_peers` blocks until SPDP has seen `min` peers.
This is useful if you want a deterministic test setup
or want to avoid a long publish loop. Not
strictly required — SEDP replay also works without it.

Spec background: the same behavior applies to Cyclone DDS and
FastDDS — their internal `create_participant` calls do not wait
for discovery either, the self-healing cycle is part of the
RTPS 2.5 discovery mechanics (§8.5.3).
